# Приёмка этапа

Самая дорогая ошибка проекта — объявить этап закрытым, когда он не закрыт: следующий этап строится на непроверенном основании, а расхождение всплывает через несколько changes, когда чинить его дорого. Поэтому приёмка — процедура, а не ощущение.

Приёмка — работа главной сессии. Субагенту не делегируется: это решение.

## Когда

Все changes этапа заархивированы. Проверить фактом, а не памятью:

```
openspec list                     # активных changes этапа не осталось
ls openspec/changes/archive       # все имена stage<N>-* на месте
```

Change следующего этапа не начинается, пока эта процедура не пройдена до конца.

## Критерий

Раздел этапов ТЗ (`docs/design.md`) называет содержание каждого этапа и его критерий приёмки. Где критерий не записан явно, критерий — перечисленные в пункте возможности, работающие на живых данных.

Выпиши критерий дословно и ответь по каждой его части отдельно: проверено, проверено частично, не проверено. «Похоже, работает» — это «не проверено».

Часть критериев проверяется только на живых данных. Это не повод их пропустить и не повод соврать: непроверенное идёт в отчёт отдельным списком, а не растворяется в «этап закрыт».

## Порядок

**1. Зелёные проверки.** Полностью, не по затронутому пакету:

```
cargo fmt --check
cargo clippy --all-targets --all-features -- -D warnings
cargo test
```

**2. Ревьюеры.** `spec-auditor` — обязательно, он сверяет реализацию с ТЗ по параграфам. `rust-reviewer` — на Rust-часть этапа. Их выводы прикладываются к отчёту; расхождение либо исправлено, либо названо отклонением с причиной.

**3. Живая проверка.** Этап, который что-то показывает или пишет, проверяется на живых данных, а не только на синтетике. Что проверить вживую не удалось — в отчёт.

**4. Знание.** Решения, принятые по ходу этапа, — в `knowledge/decisions.md`; найденные ревью дефекты и вывод из них — в `knowledge/lessons.md`; всё, где ТЗ молчит и решение принял код, — в `knowledge/open-questions.md`. Процедура — скилл `knowledge-note`.

**5. Таблица этапов и README.** В таблице состояния этапов `knowledge/stages.md` строка этапа получает «закрыт», следующего — «в работе»; правится в этом же коммите. Этим и объявляется закрытие: `knowledge/due.sh` читает таблицу. Заодно проверяется корневой `README.md` — карта репозитория, быстрый старт, команды: этап обычно приносит новый пакет или новую команду. Устаревший README врёт первым и заметен последним.

**6. Отчёт.** Короткий, три части: что сделано; что отклонилось от ТЗ и почему; что не удалось проверить без живых данных. Отчёт идёт в тело коммита, закрывающего этап.

**7. Коммит.** Отдельный коммит завершения этапа с отчётом в теле. Файлы называются поимённо.

**8. Груминг следующего этапа.** Приёмка вопросы только заводит; предъявляются они на входе в следующий этап — скилл `stage-grooming`. После коммита завершения `knowledge/due.sh --overdue` покажет то, чему настал срок вместе с закрытием этапа: вопросы, адресованные ему и его changes, стали просроченными ровно сейчас.

## Чего не делать

- Не объявлять этап закрытым при непройденной части критерия, отложив её «на следующий этап». Критерий либо выполнен, либо этап открыт.
- Не дополнять критерий из головы. Если раздел этапов звучит расплывчато — это вопрос владельцу, а не место для догадки.
- Не заменять живую проверку синтетическим тестом там, где критерий говорит о поведении на живых данных.
- Не начинать propose следующего этапа до коммита завершения текущего и до груминга (`stage-grooming`).
