# project-update Specification

## Purpose
Обновление проекта до новой версии шаблона командой `update`: трёхстороннее слияние по таблице обновления без потери правок проекта, с кодами выхода для CI (ТЗ: §How update works).

## Requirements

### Requirement: Предусловия обновления

`rootstock update` SHALL отказываться (код 1, ничего не записано), если в рабочем дереве есть незакоммиченные изменения (ТЗ: §How update works, п. 1). Целью MUST быть `--to` или последний semver-тег; если проект уже на цели — код 0 и ничего не делается (п. 2).

#### Scenario: Грязное дерево
- **WHEN** в проекте есть незакоммиченные изменения
- **THEN** `update` завершается с кодом 1 и не меняет файлы

#### Scenario: Уже на целевой версии
- **WHEN** версия в записи совпадает с целью
- **THEN** код 0, файлы и запись не меняются

### Requirement: Новые вопросы и изменённые ответы

Вопросы, добавленные новой версией, SHALL получать значение из `--data`, затем из умолчания при `--defaults`; новый вопрос без умолчания и ответа при отсутствии терминала MUST быть ошибкой (ТЗ: §How update works, п. 3). `--data` MUST менять ответ: базовый рендер идёт со старыми ответами, целевой — с новыми (§Commands, `update`).

#### Scenario: Новый вопрос без ответа и без терминала
- **WHEN** новая версия добавила вопрос без умолчания, а `--data` его не задаёт
- **THEN** код 1, файлы не изменены

#### Scenario: Смена ответа
- **WHEN** `update --data name=new` меняет ответ
- **THEN** файлы, зависящие от `name`, обновляются, а запись хранит новый ответ

### Requirement: Два рендера и таблица обновления

Обновление SHALL рендерить базу (записанный коммит, записанные ответы) и цель (целевой коммит, текущие ответы) во временные каталоги, правила классов вычисляя на каждой стороне с её ответами, и применять к каждому пути таблицу обновления (ТЗ: §How update works, п. 4–5). Для каждой строки таблицы результат MUST быть ровно тем, что в таблице.

#### Scenario: Создание нового управляемого файла
- **WHEN** файла нет в базе, он managed в цели и отсутствует в проекте
- **THEN** файл создаётся

#### Scenario: Новый управляемый файл уже есть в проекте
- **WHEN** файла нет в базе, он managed в цели и в проекте присутствует
- **THEN** при совпадающем содержимом ничего не меняется; при различии — конфликт

#### Scenario: Новый starter-файл
- **WHEN** файла нет в базе, он starter в цели, в проекте отсутствует и в инвентаре его не было
- **THEN** файл создаётся

#### Scenario: Starter удалён проектом
- **WHEN** starter-файл отсутствует в проекте, но есть в инвентаре
- **THEN** он не воссоздаётся

#### Scenario: Starter уже существует
- **WHEN** в цели файл starter и он есть в проекте
- **THEN** проект не затрагивается

#### Scenario: Проект не менял управляемый файл
- **WHEN** managed в базе и цели, проект равен базе
- **THEN** записывается цель

#### Scenario: Проект менял управляемый файл
- **WHEN** managed в базе и цели, проект отличается от базы
- **THEN** выполняется трёхстороннее слияние; пересекающиеся правки дают маркеры конфликта

#### Scenario: Проект удалил управляемый файл
- **WHEN** managed в базе и цели, в проекте файла нет
- **THEN** при base = target ничего не происходит; при base ≠ target — конфликт «deleted by project, changed by template», файл остаётся отсутствующим

#### Scenario: Шаблон убрал файл, проект не менял
- **WHEN** файл managed в базе, в цели не выпускается, проект равен базе
- **THEN** файл удаляется

#### Scenario: Шаблон убрал файл, проект менял
- **WHEN** файл managed в базе, в цели не выпускается, проект отличается от базы
- **THEN** файл остаётся, конфликт «removed by template, edited by project»

#### Scenario: Шаблон убрал файл, проект уже удалил
- **WHEN** файл managed в базе, в цели не выпускается и в проекте отсутствует
- **THEN** ничего не происходит

#### Scenario: Managed стал starter
- **WHEN** файл managed в базе и starter в цели, в проекте присутствует
- **THEN** файл не меняется и далее принадлежит проекту

#### Scenario: Starter стал managed
- **WHEN** файл starter в базе и managed в цели
- **THEN** выполняется трёхстороннее слияние с базовым рендером; шаблон забирает файл обратно

#### Scenario: Файл стал excluded
- **WHEN** файл в цели исключён или не выпускается
- **THEN** обращение как «managed → —», если он был managed, и «ничего», если был starter

### Requirement: Бинарные файлы

Для бинарного managed-файла: если копия проекта равна базе, она SHALL заменяться целью; иначе копия проекта сохраняется, цель пишется рядом как `<имя>.rootstock-new`, и это конфликт (ТЗ: §How update works, п. 6).

#### Scenario: Бинарный файл не менялся проектом
- **WHEN** проектная копия бинарного файла равна базе
- **THEN** она заменяется целью, побочного файла нет

#### Scenario: Бинарный файл менялся проектом
- **WHEN** проектная копия отличается от базы
- **THEN** копия проекта сохранена, рядом лежит `<имя>.rootstock-new`, исход — конфликт

### Requirement: Права и симлинки

Бит исполнения SHALL следовать файлу шаблона; символические ссылки MUST воспроизводиться как ссылки и не разыменовываться (ТЗ: §How update works, п. 7).

#### Scenario: Исполняемый файл
- **WHEN** файл шаблона исполняемый
- **THEN** выпущенный файл тоже исполняемый

#### Scenario: Симлинк
- **WHEN** в шаблоне лежит символическая ссылка
- **THEN** в проекте создаётся ссылка с той же целью, а не копия цели

### Requirement: Байты на входе — байты на выходе

Преобразования окончаний строк MUST не выполняться; слияние идёт по строкам, но SHALL сохранять окончания строк и завершающий перевод строки файла (ТЗ: §How update works, п. 8).

#### Scenario: Файл с CRLF
- **WHEN** файл с окончаниями CRLF сливается без конфликта
- **THEN** результат сохраняет CRLF во всех строках

#### Scenario: Нет завершающего перевода строки
- **WHEN** файл без завершающего перевода строки сливается без конфликта
- **THEN** результат без завершающего перевода строки

### Requirement: Маркеры конфликта

Маркеры SHALL быть в стиле git: `<<<<<<< project`, `=======`, `>>>>>>> template vX.Y.Z` — каждый в начале строки (ТЗ: §How update works, п. 9).

#### Scenario: Пересекающиеся правки
- **WHEN** проект и шаблон изменили одну и ту же строку
- **THEN** файл содержит блок с тремя маркерами, где версия в последнем — целевой тег

### Requirement: Хуки и новая запись

После применения таблицы `update` SHALL запустить хуки с `when` равным `update` (с учётом доверия), затем записать новую запись: новую версию, текущие ответы, новый инвентарь (ТЗ: §How update works, п. 10).

#### Scenario: Запись после обновления
- **WHEN** обновление до `v1.1.0` завершилось
- **THEN** `.rootstock.toml` содержит тег и коммит `v1.1.0`, текущие ответы и новый инвентарь

### Requirement: Коды выхода и список конфликтов

Коды выхода SHALL быть: `0` — чисто, `1` — ошибка (ничего не записано либо ясно сказано, что записано), `2` — выполнено с конфликтами. Каждый исход, названный в таблице или в правиле о бинарных файлах конфликтом, MUST давать код 2; состояния «сообщено, но чисто» нет. Конфликтующие пути с видом конфликта выводятся по одному в строке на stdout, а с `--format json` — как JSON (ТЗ: §How update works, п. 11). Диагностика MUST идти в stderr. Ошибка разбора аргументов MUST давать код 1, а не 2.

#### Scenario: Конфликт даёт код 2
- **WHEN** обновление оставило маркеры в файле
- **THEN** код 2, путь и вид конфликта напечатаны на stdout строкой

#### Scenario: Чистое обновление
- **WHEN** конфликтов нет
- **THEN** код 0 и пустой список конфликтов

#### Scenario: Побочный файл бинарника
- **WHEN** создан `.rootstock-new`
- **THEN** код 2, путь указан в списке конфликтов

#### Scenario: Неверный аргумент
- **WHEN** передан неизвестный флаг
- **THEN** сообщение clap в stderr и код 1
