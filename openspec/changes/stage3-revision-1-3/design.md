## Context

Мотивация — в proposal.md. Затронутые модули:
- края: `commands/update.rs`, `commands/import_copier.rs`, `commands/check.rs`, `commands/mod.rs`;
- ядро: `render.rs`.

Новых зависимостей между модулями нет. `check` уже может взять `apply::check_path`, как это делает `update`, а `render` меняется только внутри своего обхода. Формат записи и конфига не меняется, поэтому контракты из таблицы «Источники правды» не затронуты и `contract-change` не нужен. ТЗ уже сведено ревизией 1.3.

Как сейчас:
- `update` выходит с «already at» до любой выгрузки, а `--data` на текущей версии отбрасывает с предупреждением;
- `import_copier::run` выбирает одну сторону и при обоих файлах отказывает. Каждая сторона сама проверяет и сама пишет;
- `render` пропускает `rootstock.toml` на верхнем уровне, когда корень файлов — сам каталог шаблона. Любой путь, который рендерится в `.rootstock.toml`, для него ошибка `RecordPath`;
- `check` читает запись и ищет маркеры и побочные файлы. Путей инвентаря он не проверяет.

## Goals / Non-Goals

**Goals:**
- поведение ревизии 1.3 без нарушения правила 11 (ничего не пишется до прохождения всех проверок);
- `update` без `--data` на текущей версии по-прежнему не ходит в сеть.

**Non-Goals:**
- сверка `check` с шаблоном;
- общий рефакторинг атомарной записи и `is_release_tag` (известный долг, этот change его не трогает).

## Decisions

### D1. `update`: ранний выход только без `--data`

На текущей версии `update` выходит сразу, как раньше, если не заданы ни `--data`, ни `--data-file`. Если что-то задано, идёт обычный путь до сбора ответов цели. Затем `target_collected.recorded` сравнивается с `rec.answers`:
- совпали — «already at <version>; answers unchanged», код 0, ничего не записано, хуки не запускаются;
- не совпали — обычные шаги: план, проверки, доверие, запись, хуки, новая запись.

База — checkout `rec.commit`, цель — checkout версии, как у любого обновления.

Почему сравнение после сбора, а не по сырым `--data`: ответ, равный записанному, ничего не меняет. Ключ, который `when` выключил, тоже не меняет записанные ответы. Сравнение сырых `--data` дало бы пустое обновление с перезаписью записи.

Отвергнуто: отдельная команда или флаг. ТЗ 1.3 выбрало `--data` на текущей версии.

### D2. `import-copier`: подготовка и запись разделены

Каждая сторона делится на две части.
- `prepare_template(dir) -> TemplateImport`: текст конфига и список удаляемых файлов. Все проверки и вся конвертация — здесь.
- `prepare_project(dir) -> ProjectImport`: текст записи и `blocked`. Сюда входят чистое дерево, разбор ответов, проверка тега, выгрузка, рендер и план.
- Запись: `write_template`, затем `write_project`.

`run` при одном файле зовёт пару своей стороны. При обоих он сначала зовёт обе `prepare_*`: сторону проекта первой, потому что там чистое дерево и сеть, потом сторону шаблона. Затем пишет: `rootstock.toml` и удаления стороны шаблона, потом `.rootstock.toml` и удаление `.copier-answers.yml`. Сообщения о записи и `blocked` — как у одиночных сторон.

Инвентарь проекта считается по дереву до записи стороны шаблона. Файл шаблона ответов, который удаляет сторона шаблона, мог попасть в инвентарь проекта. Следующий `update` проведёт его по таблице как удалённый проектом, и тихой потери нет.

Отвергнуто: запустить стороны по очереди целиком. Отказ второй стороны оставил бы первую записанной, а это нарушает «nothing is written until both pass».

### D3. Рендер пропускает запись на верхнем уровне

В условии пропуска `rootstock.toml` (верхний уровень, корень файлов — каталог шаблона) рядом проверяется `.rootstock.toml`. Проверка `RecordPath` для всех остальных путей остаётся. Пропуск касается только точного имени на верхнем уровне. Короткое имя Windows (`is_short_record`) и путь, отрендеренный в имя записи, остаются ошибкой.

Почему: без пропуска шаблон, который сам проект rootstock, после двустороннего импорта не рендерится вовсе. Через `exclude` не получится: проверка `RecordPath` стоит до исключений и стоять там должна, чтобы шаблон не мог подменить запись проекта.

### D4. `check`: проверки записи без сети

До обхода инвентаря `check` проверяет версию записи.
- Она должна быть `HEAD` или `v` + semver. Иначе — строка `version <значение>`.
- Предикат выносится в `commands/mod.rs` (`is_version_name`), и его же зовёт `check_version`, чтобы правило было одно.

Для каждого пути инвентаря сначала вызывается `apply::check_path`. Небезопасный путь даёт строку `unsafe-path <путь>`, а файл не читается: ни маркеры, ни побочный файл.

Строки сортируются как сейчас, строка версии идёт первой. Код выхода прежний: находки — ошибка, код 1.

Отвергнуто: «отсутствует managed-файл». Владелец решил, что это законное удаление.

## Risks / Trade-offs

- [`update --data` с тем же ответом теперь ходит в сеть и выгружает две версии, чтобы узнать, что делать нечего] → Платит только явный `--data`. Без него ранний выход прежний.
- [Двусторонний импорт пишет четыре действия подряд. Сбой ввода-вывода посередине оставит часть записанной] → Так же, как у одиночных сторон: сообщение называет, что уже записано («… is already written, but …»). Дерево было чистым, откат — `git checkout`.
- [Пропуск `.rootstock.toml` скрывает, что автор шаблона положил туда свой файл] → Это ровно случай «шаблон — сам проект». Имя зарезервировано rootstock'ом, другого смысла у файла нет.
