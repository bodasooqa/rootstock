## Context

Мотивация — в proposal.md, решения владельца — ТЗ 1.4 и `knowledge/decisions.md` «Windows: sh из Git for Windows, режимы и ссылки из дерева git».

Как сейчас:
- `source::checkout` клонирует и выгружает commit с пользовательским конфигом git; `Checkout` несёт только путь, commit и версию;
- `render` берёт бит исполнения из `Metadata` (на не-Unix всегда `false`) и ссылку — по `symlink_metadata`;
- `apply::DiskProject` читает бит проекта с диска (на не-Unix `false`); `write_symlink` на не-Unix — ошибка; `set_mode` на не-Unix ничего не делает;
- `hooks::run_one` зовёт `sh -c`;
- библиотека собирается под `x86_64-pc-windows-msvc`, не собираются только тесты (`TemplateRepo::symlink` есть только на Unix).

Границы: `render` — ядро и читает только свои входы, поэтому режимы приносит ему `Checkout` с края `source`. git проекта трогает только край `apply`.

## Goals / Non-Goals

**Goals:**
- поведение ТЗ 1.4 на Windows без изменения поведения на Unix;
- правило 11: проверка `sh` и проба ссылки стоят до первой записи.

**Non-Goals:**
- workflow релиза и публикация;
- бит исполнения в индексе на Unix.

## Decisions

### D1. Режимы путей шаблона приходят с выгрузкой

`Checkout` получает поле `modes`: отображение пути внутри каталога шаблона (`RelPath` относительно `Checkout::path`) в режим git — файл, исполняемый файл, ссылка.
- Выгрузка commit'а: `git ls-tree -r -z --full-tree <commit>`, пути вне каталога шаблона отбрасываются, префикс снимается.
- `HEAD` локального источника: `git ls-files -s -z --full-name` (индекс), с тем же снятием префикса.
- Подмодули (`160000`) в отображение не попадают.

`render_tree` получает отображение параметром. Для пути из отображения:
- `120000` — ссылка. Цель — `read_link`, если на диске ссылка, иначе содержимое файла: так git выгружает ссылку без права на ссылки. Цель не UTF-8 — прежняя ошибка;
- `100755` — исполняемый файл, `100644` — нет. Для `.jinja` режим берётся по пути исходника.

Путь вне отображения (неотслеживаемый файл рендера `HEAD`) — с диска, как сейчас.

Для рендера `HEAD` индексный `120000` при обычном файле на диске считается ссылкой только на не-Unix, где git мог не создать ссылку. На Unix тип пути при `HEAD` берётся с диска, из индекса — только бит (находка rust-reviewer).

Цель ссылки внутри rootstock всегда хранится с `/`. На Windows `read_link` (в рендере и в `DiskProject`) меняет `\` на `/`, а создание ссылки — `/` на `\`, как Git for Windows. Иначе одна запись `120000` давала бы разные цели при `core.symlinks=true` и `false`.

Отвергнуто: `git archive` вместо выгрузки — ссылки и режимы есть в tar, но тогда нужен разбор tar и своя распаковка, и рендер `HEAD` всё равно читает диск.

### D2. Выгрузка без `autocrlf`

`git clone` получает `--config core.autocrlf=false --config core.eol=lf`: настройки ложатся в конфиг клона и действуют на выгрузку. Пользовательский и системный `autocrlf=true` (по умолчанию в Git for Windows) больше не меняет байты шаблона. `core.eol=lf` нужен для `.gitattributes` шаблона с `text=auto`: без него на Windows `eol=native` дал бы CRLF, а на Linux LF (находка spec-auditor). Явный `eol=crlf` в атрибутах шаблона действует, как у Copier: это решение автора шаблона, одинаковое на всех ОС.

Рендер `HEAD` читает рабочее дерево как есть: это файлы пользователя.

### D3. Бит исполнения проекта на не-Unix — индекс git

Только под `cfg(not(unix))`. На Unix всё остаётся как есть.
- **Рабочее дерево.** Проект — git-проект, если `git -C <проект> rev-parse --is-inside-work-tree` истинно, в том числе подкаталог монорепозитория. Наличие `<проект>/.git` не проверяется. `ls-files`, `update-index` и `add` идут с `-C <проект>`, пути — относительно проекта.
- **Чтение.** `DiskProject` один раз читает `git ls-files -s -z` проекта. Бит пути — `100755` в индексе. Индекс `120000` при обычном файле на диске — ссылка с целью из содержимого, как в D1. Пути вне индекса — не исполняемые.
- **Запись.** `pub fn set_index_modes(project, plan)` в `apply`:
  - отслеживаемый путь, чей бит отличается от плана, получает только смену режима: `git update-index --cacheinfo <режим>,<sha из индекса>,<путь>`. Содержимое в индексе не меняется, ревью правок через `git diff` остаётся целым;
  - отслеживаемый `120000`, поверх которого план пишет файл, получает `--cacheinfo 100644|100755,<sha из hash-object -w>,<путь>`: иначе git оставил бы его ссылкой;
  - неотслеживаемый исполняемый файл — `git add --chmod=+x`;
  - все вызовы — с `--literal-pathspecs` и `-c core.safecrlf=false`. Глобы в именах файлов (`*`, `[`) иначе зацепили бы чужие файлы (находки rust-reviewer и проверки безопасности);
  - пропускаются: путь, которого уже нет на диске; путь под `.gitignore` (`git check-ignore`); путь внутри подмодуля (префикс записи `160000`). Игнорируемому файлу в git не место, а подмодуль — чужой индекс;
  - сбой отдельного пути копится, проход не обрывается.
- Не git-проект — ничего не делается. На Unix функция ничего не делает.
- **Кто зовёт.** Команды, а не `apply`. `update` — сразу после записи файлов, до хуков. `new` — в самом конце, после хуков, записи и `git init`: до `git init` индекса нет, а порядок «файлы, хуки, запись, `git init`» закреплён тестом `new_git_init_failure_says_project_created`.
- `check-ignore` вызывается без `--literal-pathspecs`: git отвергает этот флаг для него, а пути он принимает буквально.
- **Сбой.** Если пути накопили сбои, команда доводит своё до конца: хуки, вывод конфликтов. Затем она завершается ошибкой (код 1): «files and the record were written; the executable bit of these paths is not in the git index: …». Так выполняется п. 11 «a clear statement of what was».

Неотслеживаемый исполняемый файл тем самым попадает в индекс. Это единственный способ сохранить бит там, где его не хранит файловая система, и ТЗ 1.4 называет индекс местом бита.

### D4. Ссылки на Windows

- **Проба до записи.** `pub fn check_symlinks_allowed(plan, root)` в `apply`. Команды зовут её среди проверок до записи: рядом с поиском `sh`, до `check_trust` и до создания каталога проекта. Если план пишет хотя бы одну ссылку, она создаёт пробную ссылку во временном каталоге в ближайшем существующем предке `root`: поддержка ссылок зависит от тома.
- **Текст отказа.** На Windows — «cannot create symlinks: enable Developer Mode in Windows settings, or run as administrator». На прочих ОС — «cannot create symlinks on this file system». Ничего не записано.
- **Порядок.** На не-Unix ссылки пишутся после всех прочих записей. Ссылка, чья цель — другая ссылка плана, пишется после неё.
- **Вид ссылки.** Если цель на диске к этому моменту — каталог, создаётся `symlink_dir`, иначе `symlink_file`. Сюда же относится висячая ссылка.
- **Замена и удаление.** На Windows ссылка на каталог снимается `remove_dir`, а не `remove_file`: перед записью поверх неё и в `Delete`.
- Запись через временный каталог и переименование — как на Unix.

### D5. `sh` на Windows

`hooks` получает поиск оболочки. На Unix это `sh`. На Windows от `git --exec-path` вверх по предкам ищутся `bin/sh.exe` и `usr/bin/sh.exe`. `PATH` не просматривается: ТЗ 1.4 называет `sh` из Git for Windows рядом с `git`, а в `PATH` может стоять чужой `sh.exe` (MSYS2, Cygwin, busybox) (находка spec-auditor).

Не нашлось — ошибка «hooks need `sh` from Git for Windows; none was found next to git». Если не запустился сам `git --exec-path`, причина добавляется к тексту.

Поиск выполняется среди проверок до записи, когда хуки фазы будут запущены: они объявлены и доверены. Найденный путь передаётся запуску. Команда без хуков к запуску `sh` не ищет.

### D6. Тесты и CI

- Тесты собираются под Windows. Помощник `TemplateRepo` получает исполняемые файлы через индекс (`git update-index --chmod=+x`), чтобы фикстура была одинаковой на всех ОС. Ссылки в фикстуре — платформенным вызовом.
- Тесты, которые проверяют режимы на диске проекта, на не-Unix проверяют индекс.
- Новые тесты, на всех ОС:
  - режим из дерева: файл `100755` в дереве, но `0644` на диске после выгрузки, выпускается исполняемым;
  - ссылка из дерева: при `core.symlinks=false` в клоне выпускается ссылкой;
  - `autocrlf`: при `core.autocrlf=true` в окружении `new` выпускает LF-файл байт в байт.
- Сквозные тесты бита и ссылок при `update` (`tests/cli_update_table.rs`) работают на всех ОС. На не-Unix бит проверяется в индексе. Добавлены случаи: бит снят шаблоном, ссылка на каталог перенацелена, проект в подкаталоге репозитория, цель ссылки с подкаталогом, файл с глобом в имени.
- `.github/workflows/ci.yml` — джоба `test` с матрицей `windows-latest`, `macos-latest`: `cargo test --locked --no-fail-fast`, а на Windows ещё `cargo clippy --all-targets -- -D warnings`. Linux покрывает джоба `rust` из `harness.yml`.
- `.gitattributes` репозитория — `* -text`, чтобы `actions/checkout` на Windows не переводил фикстуры в CRLF.

## Risks / Trade-offs

- [Проверить Windows локально нельзя] → `cargo clippy --target x86_64-pc-windows-msvc` локально ловит сборку, поведение проверяет CI на `windows-latest`.
- [Ошибку пробы ссылки на раннерах не воспроизвести: они работают от администратора] → Отображение ошибки покрывается юнит-тестом, сама проба — тем, что на раннере ссылки создаются.
- [`git add --chmod=+x` ставит новый файл в индекс] → Так решило ТЗ 1.4. Затрагивает только исполняемые файлы и только там, где у файловой системы нет бита.
