## Why

Последний change этапа 2 («Copier import and parity»). Его задача — критерий приёмки этапа (ТЗ: §Stages, п. 2, «Done when»): рендер последнего релиза harness побайтно совпадает с Copier 9.19 на всех допустимых комбинациях ответов, а обновление копии screener с harness v0.3.3 до последнего релиза даёт то же дерево, что `copier update`.

Перед propose сверка прогнана вживую. Рендер harness v0.4.5 совпал на всех 64 допустимых комбинациях, включая права файлов и симлинки. Ответы и коммит в записи совпали с файлом ответов Copier'а. В обновлении screener v0.3.3 → v0.4.5 расхождение одно, в `.claude/settings.json`, где оба инструмента дают конфликт. Подписи маркеров rootstock задаёт ТЗ, п. 9. Но отличается ещё и граница конфликта: Copier сливает через `git merge-file`, а он выносит за маркеры строку, которую обе стороны изменили одинаково. Наше слияние (крейт diffy) оставляет её внутри конфликта.

Сравнение на 3000 случайных входах дало:
- в 349 случаях конфликты расходятся по байтам;
- в 20 случаях расходится сам итог: git сливает чисто, а diffy даёт конфликт, или наоборот.

ТЗ (§Left to the builder) оставляет слияние исполнителю именно с этой оговоркой: «the builder may change it if conflict output differs from git's».

## What Changes

- Трёхстороннее слияние текста идёт через `git merge-file`, как у Copier. Конфликтные области, маркеры длиной 7, обработка CRLF и неполной последней строки — как у git. Подписи маркеров остаются по ТЗ: `<<<<<<< project`, `=======`, `>>>>>>> template vX.Y.Z` (ТЗ: §How update works, п. 8–9).
- Конфиг git пользователя и репозитория проекта (`merge.conflictStyle = diff3` и подобное) на результат слияния не влияет.
- Отказ git при слиянии — ошибка с кодом 1, до первой записи (ТЗ: §How update works, п. 11).
- Крейт diffy уходит из зависимостей.
- Сверка с Copier оформлена воспроизводимыми скриптами. Их результат — список расхождений с обоснованием — идёт в отчёт по этапу (ТЗ: §Stages, п. 2).

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `project-update`: требование о маркерах конфликта уточняется — конфликтные области совпадают с выводом `git merge-file`; слияние не зависит от конфига git.

## Impact

- **Код:**
  - `src/merge.rs` — трейт слияния вместо diffy; определение бинарных файлов и поиск маркеров остаются;
  - `src/apply.rs` — реализация через `git merge-file` рядом с `DiskProject`;
  - `src/plan.rs` — `plan_update` получает слияние параметром и остаётся чистой функцией;
  - `src/commands/{new,update,import_copier}.rs` — передают слияние и проверяют его ошибки до записи.
- **Тесты:**
  - unit-тесты слияния на векторах, снятых с `git merge-file`;
  - сквозной тест с `merge.conflictStyle = diff3` в глобальном конфиге git;
  - живая сверка с Copier 9.19 скриптами.
- **Зависимости:** минус diffy.
- **Документы:** `README.md` и `CLAUDE.md` (стек, ответственность `apply.rs`).

## Не входит

- **Подписи маркеров как у Copier** (`before updating` / `after updating`). Их задаёт ТЗ, п. 9; это расхождение с Copier перечисляется в отчёте, а не устраняется.
- **Состояние индекса git.** Copier помечает файлы с конфликтом как unmerged в индексе (`UU`), rootstock индекс не трогает. ТЗ сравнивает дерево, а не индекс.
- **Сверка в CI.** Скрипты требуют Copier 9.19 и локальные клоны harness и screener; они инструмент приёмки, а не тест.
- **Мост `harness-update.yml`** — это этап 3.
