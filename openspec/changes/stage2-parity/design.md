## Context

Мотивация — в proposal.md, раздел Why. Сейчас `merge::merge3` сливает крейтом diffy. Ширина маркера растёт, пока ни одна строка входа не похожа на маркер. Сырые маркеры diffy (`ours`/`theirs`) переписываются в подписи ТЗ. `plan_update` — чистая функция. Проект она читает через трейт `ProjectView`, на краю его реализует `DiskProject`. Ошибки чтения `DiskProject` копит и отдаёт в `finish()`, а команды зовут `finish()` до первой записи.

Copier 9.19 сливает файл проекта через `git merge-file` с подписями `before updating` / `after updating`. Уровень слияния — `ZEALOUS_ALNUM`, умолчание git для `merge-file`. На этом уровне git:
- выносит за маркеры строки, одинаковые у обеих сторон на краях конфликта;
- дробит конфликт по общим строкам внутри;
- склеивает соседние конфликты, если между ними не больше трёх строк или строки без букв и цифр.

Повторить это поверх diffy побайтно нельзя. Расходятся и сами диффы: у git свой Myers со сдвигом ханков.

## Goals / Non-Goals

**Goals:**
- Слияние rootstock даёт ровно вывод `git merge-file` при наших подписях маркеров. Состав файлов при этом не меняется.
- `merge` и `plan` остаются чистыми: git вызывается на краю.
- Результат не зависит от конфига git, окружения и рабочего каталога процесса.

**Non-Goals:**
- Свой порт xdiff или другая in-process библиотека слияния.
- Изменение правил таблицы обновления, бинарных файлов, симлинков.

## Decisions

### D1. Слияние — `git merge-file`, не in-process

Текстовое слияние запускает `git merge-file -p -L project -L base -L <target label> <project> <base> <target>`. Три входа — файлы во временном каталоге, результат — stdout. Код выхода:
- `0` — чисто;
- `1..=127` — число конфликтов;
- прочее, в том числе смерть от сигнала, — ошибка со stderr git.

Отвергнуто:
- **diffy с доработкой границ.** Выравнивание diffy по git не сходится побайтно: ханки диффа расходятся раньше, чем доходит до уточнения конфликтов.
- **gix-merge** (порт xdl_merge). Тянет стек gix и в собственных тестах держит список случаев, где расходится с git. Работает in-process, но без гарантии паритета.

git и так обязателен: источники, теги и checkout'ы идут через CLI git (CLAUDE.md, стек). ТЗ (§Left to the builder) прямо разрешает отойти от in-process слияния, если вывод расходится с git'овским.

### D2. Слияние входит в план через трейт, как `ProjectView`

`merge.rs` объявляет трейт `Merge3` с методом `merge3(&self, base, project, target, target_label) -> Merged`. Метод не падает. `plan_update` получает `&dyn Merge3` новым параметром. Реализация `GitMerge` живёт в `apply.rs` рядом с `DiskProject` и устроена так же: ошибку git записывает в `RefCell<Vec<String>>` и возвращает `Merged::Conflict` с байтами проекта. Метод `finish(self) -> anyhow::Result<()>` отдаёт накопленное.

Команды `new`, `update`, `import-copier` зовут `merge.finish()?` рядом с `project.finish()?`, до первой записи: правило 11 соблюдено. В `merge.rs` остаются `Merged`, `is_binary`, `has_markers`. Уходят `merge3` на diffy, `safe_marker_len` и `relabel`.

Отвергнуто:
- **Звать git прямо из `plan.rs`.** Нарушает границу «`merge` и `plan` чисты полностью» (CLAUDE.md, «Границы пакетов»).
- **Результат с `Result` в сигнатуре `plan_update`.** Ломает сложившийся образец с `ProjectView`/`finish` без выигрыша.

### D3. Короткие пути без git

`GitMerge::merge3` не запускает git в трёх случаях:
- `project == target` — результат `project`;
- `base == project` — результат `target`;
- `base == target` — результат `project`.

Все три чистые. Проверено против `git merge-file` на 2367 случайных входах: совпали побайтно, включая неполную последнюю строку. Без коротких путей `import-copier` запускал бы git на каждый файл проекта, совпадающий с рендером.

### D4. Конфиг git не влияет

Запуск `git merge-file` устроен так:
- рабочий каталог — тот же временный каталог;
- `GIT_CONFIG_GLOBAL` — пустой файл в нём;
- `GIT_CONFIG_NOSYSTEM=1`;
- аргумент `-c merge.conflictStyle=merge`;
- stdin закрыт.

Проверено вживую на git 2.54:
- вне репозитория `-c` не действует, а глобальный конфиг читается;
- внутри репозитория читается конфиг репозитория, и его перекрывает только `-c`. Рабочий каталог — временный, но репозиторий может прийти через `GIT_DIR`, например при запуске из git-хука.

Нужны оба приёма.

### D5. Длина маркера — 7, как у git

Маркер всегда семь символов. Растущая ширина была нужна только для однозначной перезаписи сырых маркеров diffy. С git перезаписи нет: подписи передаются через `-L`. Строка проекта, похожая на маркер, остаётся как есть, так же поступают git и Copier. `has_markers` и `check` ищут ровно семь символов, и раньше маркер длиннее семи они бы не увидели.

### D6. Сверка с Copier — скрипты в `tests/parity/`

Два скрипта `sh` берут путь к бинарнику rootstock и пишут во временный каталог.
- **`render.sh <tag>`.** Copier 9.19 и rootstock рендерят все 64 допустимые комбинации ответов `rust`, `frontend`, `monorepo`, `linear`, `telegram`, `orca`, `doc_form`. Copier берёт чистый клон harness на теге. rootstock берёт тот же тег, сконвертированный `import-copier` в рабочем дереве, и вызывает `new --version HEAD`, поэтому коммит в записи — коммит тега. Дальше `diff -r` деревьев с правами и симлинками и сверка ответов и коммита записи с `.copier-answers.yml`.
- **`update.sh <screener-commit> <tag>`.** Копия screener на коммите harness v0.3.3 обновляется двумя путями: `copier update` и rootstock `import-copier` + `update`. Расхождения деревьев печатаются; маркеры перед сравнением нормализуются в подписи Copier.

Путь к Copier, harness и screener — переменные окружения с умолчаниями. В CI скрипты не идут. `tests/parity/README.md` описывает запуск.

## Risks / Trade-offs

- **[Процесс git на каждое настоящее слияние]** → короткие пути D3 снимают все случаи без настоящего слияния. Остаются файлы, которые изменили обе стороны, — единицы на обновление.
- **[Старый git без нужного поведения]** → `merge-file` с `-p` и `-L` есть в git с версии 1.7. Уровень `ZEALOUS_ALNUM` — умолчание `merge-file` с тех же времён. Новых флагов (`--diff-algorithm`, `--object-id`) не используем.
- **[Вывод слияния зависит от версии git]** → у Copier та же зависимость. Паритет проверяется на git, установленном у владельца (2.54).
- **[Временные файлы с содержимым проекта]** → каталог `tempfile`, удаляется по `Drop`; входы пишутся только туда.
