# Журнал решений

Append-only. Решение не переписывается — отменяется новой записью со ссылкой на отменяемую. В старой записи допустима только строка-ссылка на отменившую.
Формат: дата, решение, причина, последствие. Только принятые решения; обсуждаемые варианты — в `knowledge/open-questions.md`.

```markdown
## ГГГГ-ММ-ДД · Короткая формулировка решения

**Решение.** Что именно решено, одной фразой.

**Причина.** Почему так, а не иначе. Отвергнутый вариант называется.

**Последствие.** Что теперь верно в коде и что этим сломается, если нарушить.
```

## 2026-10-30 · Git только через CLI, ревизия — тег, полный sha или HEAD

**Решение.** `source.rs` зовёт `git` одним помощником (`GIT_TERMINAL_PROMPT=0`, хуки выключены, `protocol.ext.allow=never`, `--` перед позиционными аргументами) и принимает ревизию только как имя тега, полный 40-значный sha или `HEAD` для локального источника.

**Причина.** ТЗ говорит, что версия — тег, а запись хранит точный коммит; произвольная ревизия (`main`, `-…`) открывала подстановку опций git (`--upload-pack`), найденную ревью задачи 9. Отвергнуто: libgit2 (стек проекта — CLI) и экранирование отдельных опций.

**Последствие.** `--version main` отклоняется как «не найдено». Новый вызов git, минующий помощника, теряет эти гарантии.

## 2026-10-30 · Запись проекта не ходит через симлинки

**Решение.** `apply` не пишет через симлинк-родителя (ошибка до записи), лист пишет через временный файл и `rename`, `DiskProject` читает без перехода по ссылкам; в шаблоне путь симлинка и его цель — только ASCII, цель без `~`; `rootstock.toml` и `.rootstock.toml` обязаны быть обычными файлами.

**Причина.** Пять раундов фоновой проверки безопасности в задаче 6 находили всё новые алиасы (Unicode-нормализация HFS+, короткие имена 8.3, регистр); закрыт класс целиком ограничением алфавита, а не моделированием каждой файловой системы.

**Последствие.** Шаблон с не-ASCII симлинком отклоняется при рендере. Любой новый путь записи обязан пройти `check_path` и проход по родителям.

## 2026-10-30 · Семантика планировщика обновления

**Решение.** Равенство — по содержимому (и цели ссылки), без лишних записей; одинаковые правки обеих сторон сливаются чисто; если вход шаблона в base и target совпадает, файл проекта остаётся как есть любого вида (бинарный, симлинк); все удаления выполняются раньше всех записей.

**Причина.** Ревью задачи 8 нашло, что бинарный файл или симлинк, изменённый проектом, но не шаблоном, давал конфликт при каждом обновлении. Удаления раньше записей нужны для переименований регистром и замены файла каталогом.

**Последствие.** `plan_update` — чистая функция; порядок действий — часть её контракта с `apply`.

## 2026-10-30 · Переименование только регистром — один путь

**Решение.** Пути base и target, совпадающие после свёртки (`render::fold_path`), планируются как переименование одного файла только тогда, когда файловая система их сливает: `view.get(new)` есть и равен `view.get(old)`. Во всех остальных случаях — два независимых пути по строкам таблицы, то есть удаление плюс добавление, как велит ТЗ (Non-goals, «Rename detection»).

**Причина.** Итоговое ревью нашло, что `Readme.md` → `README.md` на macOS/Windows удаляет единственный файл с кодом 0: удаление и создание из таблицы попадают в один и тот же файл. Фоновая проверка безопасности нашла, что безусловное спаривание на чувствительной к регистру ФС перезаписывает файл пользователя. spec-auditor нашёл, что спаривание без слияния имён — это обнаружение переименований, которое ТЗ исключает.

**Последствие.** На чувствительной к регистру ФС поведение буквально по таблице. На нечувствительной правка проекта переезжает в новое имя слиянием.

## 2026-10-30 · Конфликт `blocked`

**Решение.** Если путь шаблона занят тем, что проект сохраняет (файл на месте родительского каталога или каталог с файлами либо пустыми подкаталогами), запись отбрасывается, путь не попадает в инвентарь и сообщается конфликт `blocked`; позже он не предлагается заново — как удалённый проектом.

**Причина.** Таблица ТЗ предполагает, что путь свободен; без этого замена файла каталогом обрывала `update` с кодом 1 посреди записи (правило 11). Отвергнуто: удалять занявшее путь — это данные проекта.

**Последствие.** Седьмой вид конфликта в выводе CLI; вопрос о повторном предложении — в `knowledge/open-questions.md`.

## 2026-10-30 · Всё, что может упасть, — до первой записи

**Решение.** Порядок `new`/`update`: флаги, запись, git-дерево и маркеры, checkout'ы, ответы (пустые значения отклоняются), два рендера, план, ошибки чтения диска, проверка доверия к хукам, текст новой записи — и только потом запись файлов, хуки и запись `.rootstock.toml`; сбой после записи оборачивается фразой о том, что уже записано.

**Причина.** Правило 11 ТЗ. Ревью задач 11 и итоговое находили нарушения: сериализация записи после файлов, `git init` без пояснения, пустой подкаталог, ронявший `apply`.

**Последствие.** Новый шаг, который может упасть, ставится до `apply`; тест на отказ проверяет, что дерево проекта байт в байт не изменилось.

## 2026-10-30 · Проверка маркеров — только управляемые файлы

**Решение.** Отказ `update` при оставшихся маркерах и строка `markers` в `check` смотрят только управляемые файлы инвентаря, обычные файлы без перехода по симлинк-родителям.

**Причина.** ТЗ говорит «any managed file contains unresolved conflict markers»; стартовые файлы принадлежат проекту.

**Последствие.** Маркеры в стартовом файле не ловятся.

## 2026-10-30 · Рендер не нормализует окончания строк

**Решение.** Исходник `.jinja` с CRLF даёт CRLF на выходе; minijinja байты не трогает.

**Причина.** Правило ТЗ «байты на входе — байты на выходе». Jinja2 в Copier по умолчанию приводит к `\n`.

**Последствие.** Паритет с Copier на этапе 2 обязан проверить шаблоны с CRLF.

## 2026-10-30 · «Уже на версии» и `update --to HEAD`

**Решение.** При совпадении цели с записанной версией `update` выходит с кодом 0, ничего не выгружая; заданные `--data`/`--data-file` не применяются, выводится предупреждение в stderr, файл `--data-file` проверяется на чтение и разбор, а ключи `--data` против вопросов не сверяются (конфига шаблона на этом пути нет); для локального источника с `HEAD` короткого пути нет — обновление идёт всегда, база — коммит, записанный при `new`.

**Причина.** ТЗ, шаг 2: «nothing to do»; `HEAD` — движущаяся ссылка.

**Последствие.** Смена ответа без смены версии не поддерживается — вопрос в `knowledge/open-questions.md`.

## 2026-10-30 · Шаблон в подкаталоге репозитория и корень подключений

**Решение.** Локальный источник может указывать на подкаталог рабочего дерева git. Теги читаются из репозитория. Каталог шаблона — тот, где лежит `rootstock.toml`. `root`, `include_root` и проверки вложенности считаются от него. Подключения по умолчанию (`include_root = "."`) резолвятся от каталога с `rootstock.toml`, а не от `root`.

**Причина.** ТЗ: «a git repository (or a subdirectory of one)». «Template root» в ТЗ употреблён в двух смыслах: «`rootstock.toml` at the template root» и «subdirectory holding the files». Подключения harness пишутся от корня репозитория (`template/_partials/…`, как в Copier), а переход harness требует переноса «with little or no change». Отвергнуто: подключения от `root` — они сломали бы все `include` harness.

**Последствие.** Синтаксиса подкаталога для удалённого источника нет. Ключ `include_root` — расширение формата сверх ТЗ. Оба пункта — в открытых вопросах.

## 2026-10-30 · Версия от пользователя — тег semver

**Решение.** `new --version` и `update --to` принимают только `v` + semver (пре-релиз допустим) или `HEAD` для локального шаблона. Полный sha используется только внутри, для базы из записи.

**Причина.** ТЗ: «Version — a git tag …, semver `vX.Y.Z`». spec-auditor нашёл, что `--version foo` принимался при наличии тега `foo`, после чего `status` падал.

**Последствие.** Шаблон с нестандартными тегами не адресуется по ним.

## 2026-10-30 · Удалённый проектом starter не возвращается и после перерыва

**Решение.** Starter-пути старого инвентаря, которые целевая версия не выдаёт вовсе, остаются в инвентаре.

**Причина.** ТЗ: «a starter file the project deleted is never recreated». spec-auditor нашёл последовательность «удалён проектом → шаблон убрал → шаблон вернул», в которой файл создавался заново.

**Последствие.** Инвентарь может нести starter-пути, которых нет ни в шаблоне, ни в проекте.

## 2026-10-30 · Учётные данные в URL шаблона запрещены

**Решение.** Источник с паролем в userinfo или с любым userinfo в `http(s)://` отклоняется в `new`, `update` и `status`, и сообщение секрет не повторяет.

**Причина.** rust-reviewer: источник записывается в коммитимый `.rootstock.toml` и попадает в сообщения ошибок git. Отвергнуто: вырезать userinfo молча — тогда `update` не сможет достучаться до приватного шаблона, и причина будет непонятна.

**Последствие.** Приватные шаблоны требуют credential helper git.

## 2026-10-30 · Права: следует только бит исполнения

**Решение.** Запись поверх существующего файла сохраняет его биты прав (маска 0777: setuid, setgid и sticky сбрасываются) и меняет только биты исполнения — каждый бит x следует своему биту r. Новый файл получает 0644 или 0755.

**Причина.** ТЗ: «The executable bit follows the template file». Ревьюеры нашли, что режим переписывался целиком.

**Последствие.** Права проекта вроде 0600 переживают обновление.

## 2026-10-30 · Граница ядра: читает свои входы, не пишет и не говорит

**Решение.** Модули ядра (config, record, jinja, answers, render, merge, plan) читают только объявленные входы: файл конфига, запись, checkout шаблона, подключения. В проект пишет только `record` (`.rootstock.toml`). git, терминал и stderr ядру недоступны. Диалог (`TerminalPrompter`) и сообщения валидатора вынесены на край через `Prompter`. Правило в `CLAUDE.md` переформулировано.

**Причина.** rust-reviewer и spec-auditor нашли противоречие: правило «ядро не делает ввода-вывода» не сходилось с таблицей модулей, которая отдаёт record чтение и запись, а render — рендер checkout'а. Чистыми полностью остаются `merge` и `plan`.

**Последствие.** Новый вызов терминала или git из ядра — нарушение границы.

## 2026-10-30 · Артефакты OpenSpec по-русски, план — английский

**Решение.** proposal и дельта-спеки — по-русски (правило обвязки); `tasks.md` — английский план этапа без перевода; дельта-спеки не вводят поведения, которого нет в ТЗ (`blocked`, переименования регистром живут здесь, в решениях).

**Причина.** `openspec/config.yaml` требует русских артефактов; план написан до обвязки и сохранён как есть.

**Последствие.** Поведение, решённое кодом, остаётся в `knowledge/`, пока владелец не внесёт его в ТЗ.

## 2026-10-30 · Подкаталог шаблона — поле записи, ключа `include_root` нет

**Решение.** Отменяет часть решения «Шаблон в подкаталоге репозитория и корень подключений»: ключа `include_root` больше нет, подключения резолвятся от каталога с `rootstock.toml`. Подкаталог любого источника задаётся `new --subdir`. Он хранится в `.rootstock.toml` необязательным полем `subdir`, `schema` остаётся 1. `--subdir` отсчитывается от источника в том виде, как он задан, и проверяется до обращения к git; у `update` и `status` проверяется и значение из записи.

**Причина.** Ревизия ТЗ 1.1, решение владельца на груминге этапа 2. Подкаталог вынесен из URL: `//` законен внутри URL, и каждой грамматике источника понадобилось бы своё экранирование. `schema = 2` отвергнута: изменение аддитивное, старые записи читаются как есть. Подробно — design архивного change'а `stage2-template-dir` (D1–D6).

**Последствие.** Старый rootstock на записи с `subdir` падает с «unknown field» (`deny_unknown_fields`): это сознательный отказ, а не тихий рендер корня репозитория. Как сочетать локальный путь в подкаталог с `--subdir` — открытый вопрос.

## 2026-10-30 · Python-методы: набор pycompat, `append` только у `{% set x = [] %}`

**Решение.** Не-мутирующие методы строк, словарей и списков — набор `minijinja_contrib::pycompat`. Из мутирующих — только `list.append(x)`, и только у списка, заведённого `{% set name = [] %}`: этот литерал подменяется на изменяемый список rootstock при загрузке исходника. У прочих списков (литерал с элементами, результат фильтра, `namespace(x=[])`, аргумент макроса) `append` — ошибка рендера с подсказкой.

**Причина.** Ревизия ТЗ 1.2 оставляет точный набор исполнителю («The exact set: my call, the builder's»). Значения minijinja неизменяемы, литерал строится внутри движка, поэтому изменяемым можно сделать только литерал, подменённый до компиляции. Отвергнуты: собственный набор методов (дублирует pycompat), переписывание шаблона в `import-copier` (старые теги рендерятся без конвертации), форк minijinja (сопровождение). Подробно — design change'а `stage2-jinja-methods` (D1–D4).

**Последствие.** Шаблон Jinja2, который вызывает `append` у списка, созданного иначе, падает с явной ошибкой, а не рендерится тихо неверно. Если такой шаблон понадобится — расширять подмену, а не колбэк.

## 2026-10-30 · Импорт проекта Copier: чистое дерево, строгий файл ответов, `new` не конвертирует

**Решение.** Сторона проекта `import-copier`:
- требует чистого git-дерева;
- отвергает в `.copier-answers.yml` ключи, которых нет среди вопросов, и значения, которые нельзя записать в TOML (`null`, целые вне `i64`);
- о расхождениях проекта с рендером молчит, кроме `blocked` (код 2).

Конвертация `copier.yml` в памяти работает в `update` (обе стороны) и при импорте, но не в `new`. Сторона выбирается по файлам в каталоге; каталог с `copier.yml` и `.copier-answers.yml` сразу отвергается.

**Причина.** Чистое дерево продолжает правило 1 ТЗ: импорт пишет и удаляет файлы, это должно откатываться git'ом. Строгий разбор не даёт правленому руками файлу ответов тихо превратиться в запись с другими ответами. `new` без конвертации следует §Non-goals («Running Copier templates unconverted»); `update` конвертирует, потому что «Old template tags never need converting». Отвергнуты: флаг выбора стороны (нет в ТЗ), конвертация в `Side::load` для всех команд. Подробно — design архивного change'а `stage2-import-copier-project` (D1–D7).

**Последствие.** Мост harness должен коммитить импорт до `update` — открытый вопрос «Мост harness: коммит между `import-copier` и `update`». Шаблон Copier, записывающий `null` в ответ, при импорте даст ошибку с именем ключа.
